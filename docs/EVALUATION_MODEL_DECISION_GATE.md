## 为什么设置门禁

当前代码中的确定性检查、DeepEval G-Eval、单 Judge、`0.75 / 0.45` 阈值和三态路由，是为了证明数据、执行、留痕、复评和人工复核链路可运行的工程基线，不等同于已经构建出科学、客观的最终测评模型。

最终测评模型是本项目最重要的产品判断。Codex 不得独立冻结它，也不得只凭框架默认值、某个 JD 或某几条 Bad Case 反推全局标准。

## 必须先由候选人确定的第一性原则

以下问题在讨论前均保持“未决定”，本文件不预填答案：

1. 这套评测最终支持什么决策，错误的通过和错误的拒绝分别造成什么损失。
2. 被评对象和最小评测单元是什么，结论要推广到什么用户、任务和场景分布。
3. 哪些要求可以由代码或权威证据客观裁决，哪些只能由人或语义 Judge 辅助判断。
4. 质量应拆成哪些彼此可区分、可观察的维度，每个维度的正反例是什么。
5. 哪些错误是硬阻断，哪些是可补偿缺陷，哪些情况必须允许弃权或转人工。
6. 人工金标准如何形成，分歧如何解决，holdout 如何保持不被调参污染。
7. Judge 的角色是打分、分类、解释、初筛还是校验；是否需要一个或多个 Judge，以及如何处理偏差和相关性。
8. 分数是否聚合、如何加权、如何表达不确定性，以及什么证据足以支持版本发布或模型选型。

## 共创顺序

1. 候选人先用自己的语言回答上述方向问题并给出取舍。
2. Codex 基于这些方向检查内部矛盾，补充可选实现、失败模式和验证实验，不替候选人决定价值权重。
3. 候选人确认最终方向后，Codex再细化数据抽样、Rubric、确定性规则、Judge Prompt、阈值、聚合、校准和报告实现。
4. 先在评分模型验证材料上检查与候选人判断的偏差；本项目不检查重复波动。规则和执行计划冻结后，由一次主动操作运行有限矩阵并保持 holdout 参考信息密封。
5. 只有设计版本、数据版本、Judge 配置和验证证据都固定后，才运行并报告新的正式模型比较。

## 当前冻结与未冻结边界

已冻结的是工程真实性和可审计边界：运行错误不算模型失败、确定性证据优先、Judge 无权覆盖人工结论、Judge 不接收目标模型或 Prompt 身份元数据、历史工件不被覆写、凭据不进入工件、holdout 不用于反复调参。

未冻结的是科学测评模型本身：维度、Rubric、Judge 数量与角色、阈值、聚合权重、校准样本和最终发布规则。迁移前的 Chat 运行只作历史诊断，不得用来替代这一轮共同设计或新的 Responses 基准。
