# Project 3 科学测评方案第二轮假设审计

状态：审计完成；两项实现缺口已修复，产品与科学整改方向待用户审核；原工程草案继续禁止执行  
日期：2026-08-02  

## 1. 这次审计在查什么

用户指出了两个基础错误：

1. 把“有研究启发”写成“研究已经替项目决定”；
2. 把方便实施的整数写成看似科学的固定样本量。

沿着这两个错误反推，问题并不是某一句话写错，而是一种思考模式：过早把假设、设计选择和工程默认值固化成规则。此次重新检查了产品权威、口语审核版、工程草案、数据卡、评测卡、运行配置和现有实现。

## 2. 审计结论

除已经修正的“检查器分工”“样本量”以及已经暴露的单评审者限制外，又发现 12 项设计问题。其中 9 项必须在实施前修正，3 项需要候选人明确选择；另外发现的 2 项实现—文档不一致已于同日修复并完成本地回归。设计问题不会推翻现有 DeepEval + LiteLLM 工程底座，但足以使当前 EFSE 工程草案不能直接执行。

## 3. 必须修正的问题

### A01 确定性不等于客观正确

代码每次给出同样结果，只证明它可重复，不证明它测对了东西。

当前 `DeterministicCheckSpec.hard` 默认是 `true`。32 条 development 数据中，有 23 个硬 `required_terms`、15 个硬 `forbidden_terms`、3 个硬列表正则和 1 个硬语言字符启发式，共 42 个可能凭字符串或正则直接把答案判为 `FAIL` 的检查。它们可能把正确改写判错，也可能因为关键词出现在否定句中而误判通过。

整改：把确定性检查再分为：

- **完整 oracle**：JSON Schema、精确字段、明确工具参数等，合同本身足以裁决；
- **代理检查**：关键词、语言比例、正则列表、部分长度规则等，只能作为提示，除非逐项证明它与业务规则等价。

只有经过规则审计的完整 oracle 才能自动硬失败；代理检查也要用人工样本验证误放和误杀。

### A02 “证据能找到”不等于“证据支持结论”

工程草案中的代码只能检查 quote 是否出现在允许来源中。这能发现伪造引用，却不能证明引用与结论存在支持关系。

整改：把 `evidence_valid` 拆成至少两层：

- `evidence_locator_valid`：代码确认来源和原文位置真实；
- `evidence_support_verdict`：Judge 或人工判断该证据是否真的支持结论。

不得把第一层通过写成“事实有据”。

### A03 通用工作台不等于通用评测结论

工作台可以支持很多任务，但一次评测必须对应一个明确决策和目标分布。当前 40 条数据是四类任务等量拼接，36 条为合成数据、4 条来自同一个公开仓库，不能代表一般用户、一般企业或所有 LLM 应用。

整改：区分两层：

- 产品层：这是一个通用评测工作台；
- 研究层：每次运行只对预先声明的任务、用户、数据分布和配置负责。

当前 40 条只能展示工作流和发现局部 Bad Case，不能支持“模型总体更强”。

### A04 同一数据不能既调规则、选 Judge，又充当最终验证

当前 32 条 development 同时承担 Rubric 开发、阈值/策略校准和 Judge 选择；现有 8 条 holdout 又只足够做盲审流程演示。若在同一校准集上挑出最好的 P0/P1/P2，再报告同一集合上的成绩，会产生选择偏差。

整改：逻辑上至少分开：

1. Rubric/错误分类开发集；
2. Judge Prompt 与策略调试集；
3. 冻结后的 Judge meta-eval 验证集；
4. 最终应用版本比较测试集。

数据少时可以把结果明确降级为 pilot，不能通过反复复用同一批题制造“已验证”的印象。

### A05 只重复 Judge，漏掉了目标模型自身波动

当前 `RunService` 对每个 case 只生成一个目标输出；`repetitions` 只作用于 Judge。temperature 0 也不能保证所有 Provider 完全确定。因此当前设计只能看到 Judge 波动，无法估计目标模型输出波动。

整改：把最小观察单位明确为 `case × target trial × judge trial`。目标模型是否重复、重复多少次，应根据要估计的方差和先导结果决定；Judge 重复结果不能冒充独立目标样本。

### A06 当前第三组比较混淆了模型效应和 Prompt 效应

Model A + Prompt V1 与 Model B + Prompt V1 可以回答“同一 Prompt 下两种配置有什么差异”，但 weaker model + Prompt V2 同时改变模型和 Prompt，只能看组合结果，不能说明是 Prompt 补偿了模型，也不能归因给模型。

整改：先声明比较问题：

- 同 Prompt 比模型；
- 同模型比 Prompt；
- 各模型最佳生产配置比应用效果。

若要研究 Prompt 补偿，至少补齐 weaker model + Prompt V1 作为对照；需要拆分交互时再设计成完整或精简的两因素实验。

### A07 `ABSTAIN` 和 `REVIEW` 混入了不同原因

当前 `ABSTAIN` 可能表示题目证据不足、criterion 本身不清楚、Judge 没把握或引用失败；`REVIEW` 又可能表示真正语义失败、重复冲突或工程规则冲突。这些不是同一种状态。

整改：分开保存：

- criterion 是否适用：`APPLICABLE / NOT_APPLICABLE`；
- 任务证据是否足够：`SUFFICIENT / INSUFFICIENT`；
- Judge 是否完成判断：`DECIDED / UNCERTAIN / ERROR`；
- 内容判断：`PASS / FAIL`；
- 最终工作流路由：`PASS / REVIEW / FAIL / RUNTIME_ERROR`。

否则无法判断究竟是模型失败、题目失败、规则失败还是 Judge 失败。

### A08 选择 Judge 的数据不能同时报告 Judge 的最终能力

原草案比较单次、三次全体一致、三次多数并从中选最好方案，但没有另设冻结验证集。挑选本身就是调参，选完后必须在没参与选择的数据上复核。

整改：策略选择集和策略报告集分开；校准集不仅要有明显正反例，还要包含真实目标模型产生的近边界、Judge 分歧和“看起来好但实际违规”的困难样本。

### A09 “全项通过”只能说明没发现问题，不能证明答案正确

Rubric 可能漏掉重要维度，确定性规则也可能是错误代理。因此“所有 required criterion PASS”最多表示“在当前协议覆盖的检查中未发现失败”。

整改：内部可以保留 `PASS` 状态，但报告与面试必须说明它是 protocol-relative pass，不是客观真值或完整正确性证明。

## 4. 需要候选人决定的问题

### D01 Judge 是否永远不能直接语义硬失败

论文支持校准、弃权和人工升级，但没有规定语义 Judge 永远无权自动失败。这是自动化覆盖率与误判风险之间的产品政策。

候选人需要决定：在什么风险和校准证据下，Judge 只做初筛；在什么条件下可以自动通过或自动失败。未决定前保持保守 `REVIEW`，但不能把保守策略说成科学定律。

### D02 一个关键回归是否必然阻断版本

“任一 critical regression 都阻断”是风险政策，不是统计结论。它可能适合安全、事实或工具副作用任务，但不一定适合所有文本质量问题。

候选人需要按任务定义关键错误、误放/误杀成本和发布权限。不同任务可以采用不同门禁，不能把一个全局字典序当成普遍最优。

### D03 比较的到底是模型、Prompt，还是完整应用配置

三种问题都合理，但不能在一份结论中混用：

- 固定 Prompt 比模型，回答的是特定 Prompt 下的差异；
- 每个模型使用各自优化 Prompt，比的是最终应用配置；
- 同模型改 Prompt，比的是 Prompt 迭代效果。

候选人需要先选择主问题，其他比较只能作为辅助实验。

## 5. 不能再冒充科学规则的工程默认值

下列设置可以作为工程起点，但都必须标注来源和用途，不能当成研究定律：

- Judge 重复 3 次；
- 固定比较 P0/P1/P2 三种策略；
- Judge Prompt 最多修改 2 轮；
- 一个 criterion 必须拆成一次独立 API 请求；原子化要求结论可分离，不自动要求调用也分离；
- 固定使用 95% 区间；
- 固定使用 bootstrap；
- `0.75 / 0.45 / 0.20`；
- temperature 0；
- `max_tokens=1200/1000`；
- 所有模型 `reasoning.effort=max`；
- 非流式；
- 只隐藏模型名就称为完整盲评。

其中固定 seed 只能让统计代码复现，不能让抽样方法自动有效；temperature 0 不能保证 Provider 输出确定；隐藏身份元数据只能称为“metadata-blind”，模型风格或正文自报身份仍可能泄露。

允许 Judge 输出 `ABSTAIN` 是合理能力，但它自报“不确定”不等于已经校准的置信度；仍须在独立人工标签上报告风险—覆盖率关系。

## 6. 两个实现—文档不一致的整改结果

### I01 `review_floor` 未生效：已修复

- `review_floor` 现在只用于把评分结果标为 `BORDERLINE_REVIEW` 或 `LOW_SCORE_REVIEW`；达到 `threshold` 时标为 `PASS_CANDIDATE`。
- 低于阈值仍进入 `REVIEW`，不会因为语义评分模型单独低分而产生硬 `FAIL`。
- 分数区间已进入 `CaseResult`、CSV 报告和 Streamlit 结果页。
- `0.75 / 0.45` 仍是工程基线，不因此升级为已校准的科学阈值。

### I02 Responses 半截输出状态缺失：已修复

- `GeneratedOutput` 与 `ImportedOutput` 已增加 `generation_complete`、`provider_response_status` 和 `provider_incomplete_reason`。
- Provider 明确返回 `incomplete`、同步调用返回空输出，或完成状态表明未完成时，已生成内容仍追加保存，但在确定性检查和评分模型前路由为 `RUNTIME_ERROR`。
- 原因只保存受控标记，不持久化任意 Provider 错误文本；工具调用首段未完成时不会继续发送工具回传。
- 旧工件通过默认字段保持可读，但不能倒推旧 Provider 当时的完成状态。

两项整改均先增加失败复现，再修改最小路径并回归。2026-08-02 本地结果为 `51 passed`、Ruff 通过、113 个依赖包兼容；未调用在线模型。这些是工程整改证据，不是模型能力结论。

## 7. 仍然成立、无需推翻的部分

- 运行错误与模型质量分开；
- 输出、配置、规则和代码版本留痕；
- 旧工件不可覆盖；
- holdout 不用于反复调参；
- Judge 不接收显式目标模型身份元数据；
- 不把单个 Judge 分数当真值；
- 不编造真实用户、线上效果或准确率；
- 不因个别 Bad Case 无限特化全局 Prompt。

## 8. 以后制定方案的强制自检顺序

每一条规则、数字和结论在进入工程任务书前，必须回答：

1. 它是已核验事实、研究结论、项目设计、工程默认，还是尚未验证的假设？
2. 它支持的具体业务决策是什么？
3. 真正要测的对象和目标分布是什么？
4. 最小独立观察单位和有效分母是什么？
5. 数据用于开发、选择还是最终验证，是否发生复用泄漏？
6. 同时改变了几个变量，允许归因到什么程度？
7. 数字由误差、风险、功效或资源哪一个推导？
8. 可重复是否被错误地写成正确或客观？
9. 什么反例会推翻这条规则？
10. 最终措辞是否超出了保存工件真正能证明的范围？

只有上述问题有答案，才能进入可执行工程任务书。
