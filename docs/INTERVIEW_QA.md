# 真实性导向面试题与回答

> 历史题库：本文回答基于旧 40/8 + DeepEval G-Eval 工程基线，不再作为 Scientific v1 的当前口径。候选人完成真实矩阵和匿名盲审前，优先使用 `docs/DEMO_GUIDE.md` 与 `docs/PROJECT3_CURRENT_STATUS_20260802.md`；本文件中的旧测试数、三组 40 条运行和 8 条盲审待办不得当作当前事实。

这份题库优先覆盖面试官最可能核验的事实，不要求背框架内部源码。回答时只引用已经存在的文件和运行工件。

## 60–90 秒项目介绍

> 我做的是一个通用文本大模型质量评测工作台，评测对象不是单独的模型名，而是模型、Prompt、生成参数、数据集和指标配置的一个版本。  
> 
> 我把任务分成指令与文本生成、Grounded QA、多轮上下文、结构化输出与 Function Call 四类，共设计 40 条用例，其中 32 条开发集、8 条 holdout。客观项像 JSON Schema、字段值、数量和工具参数由 Python 硬规则判断；完整性、相关性和有依据性用 DeepEval 的 task-specific G-Eval。目标模型和 Judge 都通过 LiteLLM 接入。  
> 
> 工作台支持 live、冻结输出 replay 和完全本地 deterministic-only，结果分 PASS、REVIEW、FAIL，运行错误单列。Judge 没有一票否决权，争议题保留人工复核；人工确认失败后才能加入版本化回归集。CLI 是权威入口，Streamlit 用于演示和盲审。  
> 
> 这是个人 POC，数据以合成为主。目前 40 条数据合同、46 项本地测试、Responses 协议合同和离线流程已完成；旧 Chat 运行只作诊断，新的三模型运行与 8 条人工盲审尚未完成，所以我不会把离线夹具或旧协议结果当成最终模型效果。

## 1. 这个项目到底自动化了什么？

自动化了批量数据校验、模型调用、硬规则检查、Judge 评分、错误分流、结果汇总、逐题版本比较、报告和工件哈希。人工仍负责评测目标、样本、Rubric、阈值、争议题和最终业务判断。

不要只说“提效了评测”。要说清从手工动作到自动动作：

```text
逐题复制输入 -> 批量调用
手工检查 JSON/字段 -> 程序硬规则
手工汇总表格 -> 自动按任务聚合
肉眼找两个版本差异 -> case_id 逐题对齐
失败留在聊天记录 -> 人工确认后版本化回归
```

当前没有测量节省工时，所以不报百分比。

## 2. 40 条题都是什么？

四包各 10 条：

- 指令与文本生成：摘要、改写、数量、格式、长度、禁止项；
- Grounded QA：资料不足、版本冲突、例外条款、来源权威和对象绑定；
- 多轮：预算/地点/截止日更新、角色边界、指代和缺失信息；
- 结构化与工具：JSON Schema、缺失字段、枚举、天气/日程/工单工具。

每包 8 development + 2 holdout。40 条是 POC 流程规模，不是行业 Benchmark。

## 3. 数据从哪来？

36 条是明确标记的合成样本，4 条来自 Promptfoo MIT 示例并保留 URL、许可证和转换记录。不是企业数据、真实用户日志或标注团队产物。

## 4. 你怎么让不同模型得到相对一致的评分？

工程上先冻结相同输入、生成参数、Prompt、Judge 配置、Rubric 和阈值，才能做可比实验。客观项由代码精确判断；语义 Judge 只是辅助证据，还要通过重复性、人工金标准和分歧分析检验。当前单 Judge 方案只证明工作流能跑，最终如何让不同模型得到相对一致的评分，要在我先明确评测目的、误判成本和人工权威后再冻结。

需要主动补充：

> “较弱模型 + Prompt V2”同时改变了模型和 Prompt，它是提示补偿实验，不能当作纯模型排名。

## 5. 为什么当前没有直接上双 Judge？

双 Judge 不会自动产生客观真值，两个相似模型的错误还可能高度相关。当前单 Judge 只是工程基线，不是我已经排除了多 Judge。正式设计时，我会先明确判断目标与错误成本，再比较单 Judge 重复评分、异构 Judge 对照、人工金标准和分层裁决各自解决什么问题；如果第二 Judge 能提供可验证的增量证据，再加入，而不是先做多数票。

无论最终使用几个 Judge，评分时都不发送待测模型名、Model A/B 别名或 Prompt 版本，避免品牌先验影响评分；身份只在本地评分完成后对齐。模型若在回答正文中主动自报身份，则作为被评行为保留。

## 6. Judge 自己不稳定怎么办？

当前基线计划对固定开发样本重复评分，并把波动、Judge 失败和人工分歧分别记录；Judge 失败是 RUNTIME_ERROR，低分不自动变成硬 FAIL。具体样本数、重复次数和波动阈值仍要在科学测评模型共创时根据误判成本和校准证据确定。

当前要如实说：

> 稳定性链路和配置已经实现，但新的 Responses 合同尚未真实复跑，科学测评模型也未冻结，所以还没有可报告的正式波动数字。

## 7. 为什么 Judge 不能直接 FAIL？

语义 Judge 是概率模型，可能受措辞、顺序和自身知识偏好影响。JSON 类型、固定字段和工具参数可客观失败；开放语义低分先进入 REVIEW，避免把 Judge 偏差误写成被测模型硬失败。最终语义 FAIL 需要人工理由。

## 8. 离线复评是不是通用做法？

是。目标生成和评测应解耦：修改 Rubric、阈值或排查 Judge 时，用相同输出重评，才能只改变一个变量。项目通过 output hash、generation config hash 和 source run ID 证明输出没变。离线复评不能冒充新模型运行。

## 9. live、replay、deterministic-only 有什么区别？

- live：目标模型重新生成，硬规则和 Judge 都运行；
- replay：输出不变，硬规则和 Judge 重跑；
- deterministic-only：输出不变，只跑本地硬规则，不发网络请求。

deterministic-only 的 `coverage_complete=false`，所以不能冒充完整语义验收。

## 10. 一个具体 Bad Case 是什么？

离线演示中的 `GQ-003` 问资料未提供的保修期。故意错误输出说“一年保修”，同时：

- 没有出现“资料未说明/无法确定/证据不足”；
- 出现禁止臆造的“一年保修”。

它被两个确定性检查定位为硬失败。这个例子是人工合成夹具，不是真实模型结果。

真实模型运行后，应换成真实 run 中的实际 Bad Case。

## 11. 失败后怎么定位根因？

按阶段排查，不先改 Prompt：

1. 数据是否有效、预期和 Rubric 是否自洽；
2. 目标生成是否超时、空响应或工具格式错误；
3. 硬规则是否错误地匹配或漏判；
4. Judge 是否报错、低分或重复评分波动；
5. 目标输出是否真的违反业务目标；
6. 最后才判断是 Prompt、模型能力还是样本边界。

运行错误不算模型质量失败，Judge 争议不直接硬 FAIL。

## 12. 这个项目与 RAG 有关系吗？

不是 RAG 系统。Grounded QA 用例会给固定 context，用于测“只依据提供资料回答”，但项目不做检索、切分或向量库。这样能单独评估回答层，不把检索问题混进来。

## 13. LiteLLM 做什么？

LiteLLM 是目标模型和 Judge 的统一路由层。配置使用 provider-prefixed model name、API Key 和可选 Base URL 前缀，但项目执行层只调用 `/responses`，不使用 Chat Completions；自定义 URL 通常填到 `/v1`，终端路径由 LiteLLM 追加。它不代表所有云 IAM、中转站或模型都已经验证，真实 Provider 必须先做 Responses probe。

## 14. DeepEval 做什么？你自己做了什么？

DeepEval 提供 `LLMTestCase` 和 G-Eval 执行框架；LiteLLM 提供模型路由，项目代码补了受测试的 Responses Judge 适配。

我负责的是产品和评测层：

- 四个任务包与 40 条数据合同；
- Schema，以及当前用于验证工程链路的 Rubric、阈值和三态基线；
- 哪些交给硬规则、哪些交给 Judge；
- live/replay 分离；
- 人工盲审和回归门禁；
- 结果解释与真实性边界。

最终科学测评模型尚未冻结。我需要先能从第一性原理解释评测目的、误判成本、维度、人工权威和 Judge 角色，再与 AI 协作补足实现；不能把框架默认配置包装成我已经完成的方法论。

工程代码使用 AI 工具辅助完成，但我需要能亲自启动、改配置、复现 Bad Case 并解释。

## 15. 为什么不用 Promptfoo 或 Inspect AI？

Promptfoo 更适合大规模 Provider 配置矩阵、红队和 CI；Inspect AI 更偏研究级 Solver/Scorer 和安全评测。这个 POC 更需要 Python 内直接组合数据、硬规则、DeepEval 指标和 Streamlit，因此 DeepEval 的学习与实现成本更合适。

当前安全回答：

## 17. 项目成功标准是什么？

不是模型 100% 通过，而是：

- 流程能运行；
- 结果可解释；
- 错误能定位；
- 版本能比较；
- 失败能回归；
- 自动与人工边界清楚。

## 18. 项目最大限制是什么？

40 条且以合成为主，当前语义评分仍是待校准的单 Judge 工程基线，首版只有文本，没有真实线上流量和生产权限。它适合证明评测工作流与方法设计过程，不适合直接做生产选型或声称模型总体准确率。

## 19. 如果面试官让你现场改一个东西

推荐改：

- 把 `judge.threshold` 从 0.75 改为 0.80，然后对同一输出 replay；
- 修改一条 JSON Schema，观察确定性结果；
- 在 Prompt V1/V2 间解释变量变化；
- 对一个已确认开发集 Bad Case追加人工分类并提升回归。

不要现场打开或展示 API Key，不要修改 holdout 参考答案来“调通过”。
