# Scientific v1 10 分钟演示手册

## 演示前准备

候选人必须先亲自完成：启动界面、查看数据台账、解释一条直接规则和一条语义规则、运行一次离线验收、完成真实矩阵后的匿名盲审。没有亲自完成前，只能说“我确定了产品方向，工程由 AI 辅助实现，我正在复现掌握”。

准备命令：

```powershell
cd minos-bench
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File .\scripts\run_scientific_offline_acceptance.ps1
.\scripts\start_ui.ps1
```

离线验收不会读取 profile 或调用真实 Provider。真实矩阵只运行已经批准的一次有限执行；不要现场临时创建第二轮。

## 0:00–1:00：为什么做

推荐口述：

“我之前的 POC 暴露出一个问题：如果把单个 Judge 的自然语言意见当成唯一验收门槛，很难区分业务缺陷、评分模型偏差和运行错误。我把它重构成一个通用 LLM 应用评测工作台：先追溯题目来源，再把能直接证明的合同、只能提示风险的信号、语义初审和人工裁决分开，最后用有限矩阵和匿名复核做版本比较。”

不要说训练了模型、做了生产平台或得到企业效果。

## 1:00–2:30：数据和来源

展示 `datasets/scientific_v1/source_ledger.jsonl`、`manifest.json` 和 `seal.json`。

讲清：

- 38 个问题实例按五种用途隔离，另有 14 份 Judge 固定回答；
- 25 个正式比较题覆盖四类应用任务，分布 6 / 7 / 5 / 7；
- IFEval/BFCL 只在许可证允许范围内作锚点改编，其余多为方法迁移或自建题；
- 没有逐题来源的旧 16 道草案被排除；
- 同一 scenario family 不能跨规则开发、Judge 验证和正式比较。

## 2:30–4:00：规则和裁决权

在匿名复核页任选一题，解释：

- `DIRECT_VERIFIER` 只验证计数、Schema、工具调用、环境状态等可机械证明事实；
- 关键词和长度启发式是 `SIGNAL_ONLY`，不能直接证明语义失败；
- 原子 Judge 一次只判断一个登记行为，给出答案证据和来源证据；
- Judge JSON 由提示词请求并在本地解析；解析或字段组合失败记为运行错误，既不计内容 0 分，也不自动修复或追加第二次 Judge；
- Judge 的 FAIL 进入人工复核，不直接淘汰版本；
- 严重直接合同失败或候选人确认的严重错误才阻断版本。

面试官追问“怎么让不同模型评分一致”时，不要回答“换更强 Judge”。应回答：先固定题目、证据、原子边界和输出合同，用 14 份正反固定回答检查误报、过度确定、逃避弃权、引用和状态错配，再把分歧交给匿名人工确认。

## 4:00–5:30：有限执行器

展示 `configs/scientific_v1.json` 和执行计划，不展示加密 profile。

```text
4 Provider probes
+ 6 技术路径请求
+ 14 Judge 体检
+ 100 target
+ 100 formal Judge
= 224 个计划成功请求
```

讲清：四槽健康检查只是 LiteLLM `ping`，任意非空响应即成功，不承担 Judge 校验；每题每配置生成一次、每答案评分一次；LiteLLM 内部自动重试关闭，由执行器对超时、429、5xx 只重试当前请求直到成功；质量差不触发重生成、扩题、第二 Judge 或下一轮；Provider 硬合同错误首次停止，Judge 解析错误记录后继续；相同完成执行编号重进不会重复调用；已成功的健康探针可用协议绑定收据复用。

## 5:30–7:00：报告

真实运行和候选人盲审前，只展示离线验收工件，不展示不存在的模型结论。

真实运行完成后可先说明机器报告包含：

- 四任务包等权参考分；
- 完成率、判断覆盖率和人工覆盖率；
- 机器复核候选与候选人确认错误分开；
- 同题修复、退步、持平和不可比较；
- 运行错误不作为内容 0 分，ABSTAIN 不计分但降低覆盖率。

候选人盲审前不要打开机器报告给自己看，以免破坏盲法。

## 7:00–8:30：匿名人工复核

展示第六页“科学版匿名盲审”：

- 页面不显示目标模型、配置、Prompt 或 Judge 结论；
- 逐原子小项选择 PASS、FAIL、需要更多证据或不适用；
- 每项必须写证据理由；
- 记录追加保存，不覆盖历史；
- 全部匿名项完成前，CLI 拒绝生成候选人确认报告。

强调个人 POC 只有一名候选人参考判断，不能包装成专家 gold 或大规模标注团队。

## 8:30–10:00：局限与下一步

推荐口述：

“这个项目自动化的是数据合同校验、固定矩阵调用、直接规则检查、Judge 证据整理、运行错误隔离、同题比较、报告和盲审编排。人工保留的是题目业务含义、争议裁决、严重问题确认和最终版本建议。当前数据以公开和合成为主，每配置每题只跑一次，模拟工具不代表真实系统，所以结论只适用于冻结题目和当次配置。后续只有人工确认的真实失败才会进入新回归版本。”

## 常见真实性追问

### 为什么不用双 Judge？

首版最重要的是先把规则原子化、验证 Judge 合同并建立人工参考。两个未经校准的 Judge 可能只是放大同类偏差，不能自动得到客观真值。

### DeepEval 在哪里？

DeepEval G-Eval 保留为早期工程基线和失败审计。Scientific v1 的正式评分改为一次 `/responses` 原子 Judge，因为旧 G-Eval 会为一个指标发出多次请求，成本、超时和归因都不适合当前有限矩阵。

### 自动化了什么？

自动完成来源/schema 门禁、冻结计划、批量调用、机械合同、Judge 证据整理、错误分层、版本对比、报告和匿名任务编排；人工从逐题重新组织全流程，转为判断争议和高风险小项。没有真实工时基线，所以不报节省百分比。

### 你本人做了什么？

必须按事实回答：候选人确定了项目方向和关键产品裁决；研究、数据转换、代码、测试与文档由 Codex/AI 辅助完成；候选人需亲自复现、盲审、解释坏案例和演示。不要把 AI 辅助代码说成全部手写。

## 故障预案

- profile 不可用：停止，不现场重填或展示 Key。
- 400/参数不支持：按硬合同错误停止，不改协议硬跑。
- 超时/429/5xx：执行器只重试当前请求直到成功，不新增题目或答案版本。
- Judge JSON 错误：记为运行错误，不计内容 0 分，不偷偷再问一次，并继续剩余矩阵。
- 真实矩阵未完成：只演示离线验收和假 Responses 控制流，不展示模型排名。
