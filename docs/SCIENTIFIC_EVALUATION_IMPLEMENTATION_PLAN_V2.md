# Project 3 面试级科学评测实施计划 v2

状态：已由 `SCIENTIFIC_EVALUATION_IMPLEMENTATION_PLAN_V3_APPROVED.md` 取代；仅作方案演进记录，不再执行  
日期：2026-08-02  
目标：形成面试级可信证据，同时让构题、评分、坏案例归因和版本决策体现成熟评测团队的方法质量  

## 1. 已批准的产品决定

1. 主项目比较完整 AI 应用版本；需要解释模型或提示词贡献时，另做一次只改变一个变量的小实验。
2. 完整、可直接核对且提前定义为严重的代码规则可以自动阻断。
3. 高风险语义问题必须人工确认；低中风险语义问题只有独立验证后才允许自动处理一部分。
4. 严重回归只有在“提前定义 + 完整代码规则或人工确认”时阻断版本；评分模型单独报警只进入复核。
5. 当前 40/8 只按工程工作流、构题审计和先导材料解释，不承担统计推广。
6. 不做掩盖严重错误的统一总分。
7. 关键词、正则和字符比例默认只是风险信号，逐条证明等价后才可直接裁决。
8. 引用存在与引用支持结论分开判断。
9. 规则开发、评分策略选择、评分模型验证和最终比较的数据用途分开。
10. 待测模型和评分模型重复几次，由先导波动决定。
11. 单人判断只叫候选人参考判断。
12. 完成标准选择“面试级可信证据”，不追求统计保证；方法设计仍按成熟大厂评测岗位水准执行。

## 2. 项目最后要证明什么

面试时要让人看到五项真实能力：

1. 能从业务决策反推评测目标和错误成本；
2. 能构建有正常、边界、诱骗、最小对照和历史坏案例的题集；
3. 能区分代码核验、语义初审和人工裁决；
4. 能验证评分模型，而不是盲信评分模型；
5. 能把失败归到数据、模型、提示词、工具、评分器或运行环境，并沉淀为回归资产。

不需要证明：某个基础模型在普遍意义上最好、评分模型达到生产可靠性、结果代表真实大厂流量或项目产生真实 ROI。

## 3. 比较设计

### 3.1 主比较

主比较使用两套完整配置：

- 应用版本 A：Model A + Prompt V1 + 固定生成参数；
- 应用版本 B：Model B + Prompt V1 + 相同生成参数。

结论口径：在当前任务、题目和配置下，两套应用版本的逐题差异。由于除模型外其余主要条件相同，也可以谨慎讨论模型选择带来的差异，但不能推广成通用模型排行榜。

### 3.2 提示词控制变量实验

新增：

- weaker model + Prompt V1；
- weaker model + Prompt V2。

同一个模型只改变提示词，用于展示如何根据错误分析修改提示词并验证是否修复特定问题、是否产生新回归。

旧的“Model A 对 weaker model + Prompt V2”只能比较两个组合，不用于解释提示词补偿或模型能力。

## 4. 构题方法

### 4.1 能力—风险—样本矩阵

每道题必须绑定：

- 任务包与具体能力；
- 用户或业务要完成的目标；
- 可能失败的行为；
- 错误严重程度与理由；
- 测试类型；
- 可用证据；
- 检查方法与裁决权限；
- 数据用途；
- 来源和版本。

总题数不预先写死。先完成矩阵，再根据空缺、重复和无效题决定保留、修改或新增多少题。

### 4.2 每个高价值能力至少考虑的测试类型

1. 正常任务：基本能力是否成立；
2. 边界任务：资料不足、条件冲突、规则不适用或接近限制；
3. 明确失败：应该拒绝、澄清或转人工的情况；
4. 最小对照：只改一个关键条件，正确结论应变化；
5. 不变性：只改措辞、顺序或无关信息，正确结论不应变化；
6. 诱骗样本：答案流畅、格式正确或引用真实，但核心行为错误；
7. 历史坏案例：来自真实运行后经人工确认的问题。

不是每个普通能力都机械凑齐七种题。高风险能力优先，低价值重复题删减；覆盖表必须解释取舍。

### 4.3 四类任务的重点

#### 指令与文本生成

- 数量、格式、范围、禁止项和角色约束；
- 信息完整与无依据补充；
- “更好看但违背指令”的诱骗答案；
- 改写后含义不变的不变性测试。

#### 有依据问答

- 资料中有答案、没有答案、互相冲突和只有部分答案；
- 引用是否存在；
- 引用是否真正支持结论；
- 否定、限定、例外和跨段证据；
- 看似相关但实际不支持的干扰证据。

#### 多轮对话

- 旧约束保留、新约束覆盖和用户撤销约束；
- 指代、角色边界和信息跨轮一致；
- 无关历史干扰；
- 关键条件只改变一处的多轮最小对照。

#### 结构化输出与工具调用

- 结构、字段类型和必填值；
- 是否该调用工具、选哪个工具；
- 参数、顺序和工具结果使用；
- 运行失败、工具无结果和需要确认的副作用；
- 格式完全正确但工具选择错误的诱骗样本。

## 5. 检查器和裁决权

### 5.1 代码检查分两类

`DIRECT_VERIFIER`：业务合同本身足够直接裁决，例如 JSON Schema、明确枚举、已确认工具名和参数、引用编号真实存在。

`SIGNAL_ONLY`：关键词、正则列表、语言比例、长度和其他启发式，只提示风险，不直接失败。

每条代码检查还要单独保存风险等级。检查方法和严重程度不能共用一个 `hard=true` 字段代替。

### 5.2 语义评分项

每条语义评分项必须包含：

- 唯一编号；
- 适用条件；
- 要观察的单一行为；
- 什么算通过；
- 什么算失败；
- 什么情况证据不足；
- 允许查看的证据；
- 正例和反例；
- 风险等级；
- 最终裁决是否必须由人确认。

## 6. 新评分模型合同

旧 G-Eval “整题 0—1 分”保留为历史工程基线，不作为最终主裁决。

新合同采用一次结构化请求判断同一题的多个原子评分项，避免每个评分项各发一次请求，也避免 DeepEval 每题临时生成评估步骤造成额外调用和波动。

每个评分项返回：

```text
criterion_id
applicability: APPLICABLE / NOT_APPLICABLE
evidence_sufficiency: SUFFICIENT / INSUFFICIENT
decision: PASS / FAIL / ABSTAIN
answer_evidence: 回答中的具体片段
source_evidence: 允许证据中的具体片段或编号
reason: 简短理由
```

代码验证：

- 所有要求的评分项都返回且没有多余编号；
- 证据片段确实存在；
- 不适用、证据不足和评分模型无法决定没有被混为同一种失败；
- 评分模型输出不包含目标模型身份元数据；
- 运行未完成或结构无效单独记为运行故障。

评分模型只负责语义初审和证据整理，不覆盖直接核验结果或人工判断。

## 7. 单题与版本路由

按顺序处理：

1. 接口、截断、空输出或评分器异常：运行故障；
2. 提前定义的严重直接核验失败：确定失败；
3. 高风险语义疑似失败：人工复核；
4. 评分模型弃权、证据不足、结果冲突或风险信号触发：人工复核；
5. 所有适用项在当前规则下通过：候选通过；
6. 最终对外结论仍说明“按当前协议未发现问题”，不称客观完全正确。

版本比较使用同题配对：修复、退步、持平和无法判断。严重回归必须预先定义，并由直接核验或人工确认后才阻断。

## 8. 怎样验证评分模型

面试级目标不声称统计可靠性，但必须真实做一轮小型评分模型体检：

1. 用清晰正确、清晰错误和边界/证据不足材料检查基本执行；
2. 加入真实目标模型输出，而不是只用手写理想样本；
3. 检查最容易误判的诱骗答案；
4. 对相同内容做措辞改写，检查结论是否无故变化；
5. 若进行成对比较，交换展示顺序检查位置偏差；
6. 分别记录误放、错杀、弃权、覆盖和运行故障的原始分子/分母；
7. 数据很少时只展示逐题表和限制，不输出看似精确的“准确率”。

候选人需要盲审由覆盖矩阵选出的材料。具体数量由矩阵中的必要分层产生，不预先把任意整数写成科学门槛。

## 9. 分阶段运行与止损

### 阶段 0：完全离线

- 数据合同、能力风险矩阵、直接核验/风险信号审计；
- 新评分项 Schema、路由、报告和模拟输出测试；
- 全量本地测试、界面冒烟、依赖和运行时身份检查。

### 阶段 1：Provider 探针

- 只在科学方案冻结和一次性预算授权后运行；
- 每个待测槽位一次最小生成，评分模型一次结构化合同；
- 任一失败即停止，不进入样本运行。

### 阶段 2：开发集小样本试跑

- 每类任务选择一条能覆盖主要输入形态的开发题；
- 先验证完成状态、工具回传、评分结构、证据和请求统计；
- 完成后停止并审查，不自动进入完整运行。

### 阶段 3：开发材料运行

- 先跑应用版本 A；通过运行质量审计后再跑应用版本 B；
- 提示词控制变量实验独立运行；
- 同一失败连续三次触发熔断；每次运行受请求预算限制。

### 阶段 4：评分模型体检与人工参考判断

- 评分策略选择材料和最终检查材料分开；
- 候选人完成盲审；
- 结果不足时缩小自动裁决范围，不无限修改提示词追求全通过。

### 阶段 5：封存题一次性运行

- 数据、评分项、路由、代码和运行配置全部冻结后才解封；
- 不因结果不好回头修改后再次使用同一封存题；
- 候选人完成盲审后生成最终面试证据。

## 10. 错误闭环强制规则

执行时必须同时读取 `FAILURE_LOOP_AUDIT_AND_GUARDRAILS_20260802.md`：

- 每次失败先做最小复现和层级归因；
- 一轮只改变一个变量；
- 同一根因假设第二次修复仍失败，停止补丁并审计测试答案和架构；
- 同一失败签名第三次出现，禁止继续在线运行；
- 没有新证据不得再次整套运行；
- 一次性运行授权消费后不能复用。

## 11. 需要修改或新增的工件

### 数据与配置

- 能力—风险—样本覆盖表；
- 每题数据用途、测试类型、风险、证据和检查权限字段；
- 原子评分项配置；
- weaker model + Prompt V1 对照配置；
- 用户确认的科学方案冻结；

### 代码

- 确定性检查的 `DIRECT_VERIFIER / SIGNAL_ONLY` 权限；
- 结构化原子评分模型；
- 状态分层和证据验证；
- 同题配对比较；
- 请求预算、连续错误熔断和一次性授权；
- 报告与 Streamlit 中文展示。

### 证据

- 数据覆盖审计；
- 测试答案质检记录；
- 评分模型逐题体检表；
- 小样本试跑与停止决策；
- 候选人盲审；
- 至少一个真实坏案例的根因和回归；
- 最终限制说明。

## 12. 完成标准

### Codex 可以完成

- 全部离线设计、代码、测试、数据审计、报告模板和止损机制；
- 在得到一次性授权后执行约定的在线阶段并保存真实工件；
- 根据源证据与人工判断生成面试材料。

### 候选人必须完成

- 审核最终能力—风险地图和严重错误；
- 完成要求的盲审与争议题判断；
- 每阶段真实在线调用前确认调用计划与预算；
- 亲自启动项目、解释一个坏案例并完成约 10 分钟无稿演示。

### 最终可以声称

完成了一个通用 LLM 应用评测工作台，并以能力风险矩阵、直接核验、原子语义评分、人工升级、同题配对、坏案例回归和运行止损组成可审计评测流程。

### 最终仍不能声称

评分模型达到生产可靠性、结果代表真实大厂流量、某模型普遍最佳、存在真实企业客户或产生未经测量的效率和 ROI。
